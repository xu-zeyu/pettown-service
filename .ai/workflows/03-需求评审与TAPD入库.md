# 工作流 03：需求评审与 TAPD 入库

## 目标

对需求池进行评分和反方质疑，将用户授权入库的需求转化为正式、可追溯的 TAPD 需求，并在创建成功且通知目标已确认后发送企业微信群通知。执行本流程时加载 `../skills/tapd-requirement-intake/SKILL.md`。

## 执行步骤

1. 读取需求草稿或用户目标，确认项目 ID 和产品范围；核对 TAPD 工作空间名称、ID 与现有需求。
2. 查询 TAPD 是否存在重复或关联需求、缺陷。
3. 补全背景、用户痛点、场景、功能范围、业务规则、异常情况、权限、数据/API 影响、验收标准、优先级和风险。竞品证据须写明来源日期，不能代替本产品业务事实。
4. 每项从价值 V、紧急度 U、可行性 F、战略匹配 S 四维各打 1–10 分，计算 `Score = round((0.4V + 0.3U + 0.2F + 0.1S) × 10)`。主张方给出依据，质疑方检验替代办法、复用点、成本与风险。85–100 分建议 P0、75–84 分建议 P1；低于 75 分暂缓，不计入本次合格需求池。评分须有证据，产品判断及例外写明理由，但不得将低于 75 分的条目算作达标。
5. 入库前核对去重后的合格需求至少 20 条，且每条评分不低于 75 分，具备来源和可验收描述。关键业务规则未确认的条目标为待确认，不得自行编造或计入合格条数。未达标时保留草稿并报告缺口，不启动该批次入库及通知。负责人默认使用当前项目配置中的 `tapd.default_owner`；单条需求有用户明确指定时覆盖。若用户尚未授权正式入库，先提交完整需求供审批；若用户已明确要求入库，在其授权范围内直接继续，不重复索取批准。
6. 使用已核实可用的 TAPD Skill 或连接器创建/更新事项。写入负责人前先在已核实的 TAPD 项目空间查询成员，确认姓名唯一匹配并使用工具要求的成员标识；找不到或存在歧义时暂停该条入库并报告，不猜测账号。创建结果不明确时，先按项目和标题查询，确认是否已经创建，避免重复入库。
7. 回读 TAPD 记录，核对真实需求 ID、标题、项目名称、描述、优先级、负责人、创建时间和可访问的详情链接；分别记录创建调用与回读结果。负责人须与本条预期一致；未分配或不一致时如实报告并核查，不宣称该条完成。
8. 如用户已授权通知，先核对目标研发群名称及对应群聊标识或机器人配置。用户明确指定固定机器人配置为目标时可据此发送；不得在文档或回执中记录机器人密钥。确认每个需求 ID 对该目标尚未发送过成功通知；通知目标不明时不发送。
9. 仅当 TAPD 明确创建成功，且回读得到真实需求 ID、标题和有效详情链接后，使用已授权的企业微信消息能力发送通知。每条需求发送一次；发送后核对 HTTP 状态和企业微信业务成功码，记录目标群、需求 ID、发送时间及真实回执。发送结果不明确时先核实，不盲目重试。
10. 将需求池及入库记录归档到 `requirements/approved/`，关联 TAPD 创建、回读及通知执行记录；分别报告合格需求总数、实际入库数、未入库原因与通知状态。若部分创建或回读失败，如实标记本批次未完成，不以本地编号代替 TAPD ID。

## 企业微信群通知格式

```text
【新需求创建通知】

项目：{项目名称}

需求标题：{需求标题}

需求 ID：{需求ID}

优先级：{优先级}

负责人：{负责人；未分配时写“未分配”}

需求描述：
{需求描述或忠实摘要}

创建时间：{创建时间}

需求详情：
{TAPD需求链接}

通知来源：WorkBuddy
```

## 限制

- TAPD 创建失败时停止通知，保留草稿并说明实际原因；缺少 ID 或链接时先查询详情。不得伪造 TAPD 信息或把本地记录当作实时状态。
- 企业微信授权失效、找不到目标群或群聊映射未确认时停止发送并说明原因；发送失败不得报告成功。同一需求对同一群不得重复发送成功通知。
- 不在需求文档、执行记录、日志或答复中写入机器人 Webhook 密钥、TAPD 令牌或其他凭证。
