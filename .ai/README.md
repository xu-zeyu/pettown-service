# 多项目、多技术栈 AI 研发工作空间

本 `.ai` 目录是一套供多个代码仓库共同使用的 AI 研发工作规范与流程模板。

**设计原则：通用规则集中维护，项目差异通过 YAML 配置，项目业务知识彼此隔离。**

## 一、目录分层

- `core`：所有项目共用的基本规则、审批要求和工具使用规范。
- `agents/研发Agent.md`：研发 Agent 的执行入口，包含开发前读取、逐需求分支、红绿对抗自测和合并闸门。
- `agents/原型Agent.md`、`agents/ArdotUIAgent.md`：从 TAPD 需求依次产出原型思维与 UI 图片。
- `agents/测试Agent.md`：模块测试入口，约束 Apifox 上传回读先行、关联链路验证和禅道 Bug 入库回读。
- `workflows`：跨技术栈通用工作流。执行前必须读取当前项目配置。
- `config`：工作空间配置、项目注册表和技术栈配置。
- `projects`：每个项目一份独立 YAML 配置。
- `project-knowledge`：项目专属知识，不得混入其他项目的业务资料。
- `templates`：需求、技术设计、任务拆解、测试和交付模板。
- `requirements`：候选需求和审批归档。
- `skills/tapd-requirement-intake`：需求评分、TAPD 入库回读与企业微信通知。
- `skills/tapd-version-delivery`：版本 TAPD 清单、P 级排序、逐项分支开发与审查自测合并、开始/完成通知。
- `skills/api-regression-testing`：模块接口自动化测试闭环（接口识别、Apifox 导入回读、红绿对抗用例、禅道 Bug 入库、运行报告）。
- `agents/禅道Agent.md`、`skills/zentao-bug-intake`：使用禅道官方 API V2 核实产品、查重、创建 Bug 并回读；凭证与 Apifox 分开配置。
- `skills/wecom-notification`：研发、需求、UI、测试共用的企业微信群目标核实、发送与回执规则。
- `skills/ardot-ui-delivery`：UI 排重台账、Ardot 入项回读与企业微信通知。
- `runs`：需求执行过程中的产物与证据。

## 二、在 WorkBuddy 中使用

1. 在 WorkBuddy 中打开目标项目或包含多个项目的工作空间。
2. 首先读取本目录的 `README.md`、`config/workspace.yaml`、`config/projects.yaml`。
3. 明确本次任务对应的项目 ID，再读取 `projects` 下对应的项目配置。
4. 研发任务先读取 `agents/研发Agent.md`，再按其中顺序读取项目架构、相关技术栈配置、约束和工作流文件。
   “生成 <版本> 版本需求”走需求入库 skill；“开始 <版本> 代码编写”走版本研发 skill，按清单逐项执行。
5. 优先使用 WorkBuddy 中已经安装并连接的 Skills、TAPD 和企业微信能力。
6. 涉及需求正式入库、技术方案定稿、代码修改、数据库变更、Git 提交或发布时，遵循人工审批要求。

注意：不能默认 WorkBuddy 会自动加载 `.ai`。除非已验证项目指令加载机制，否则每次任务都应明确要求 WorkBuddy 先读取相关文件。

### 流程与审批节点

| 阶段 | 工作流 | 主要产物或动作 | 本阶段审批门槛 |
|---|---|---|---|
| 项目扫描 | `01-项目扫描与画像.md` | 项目知识草稿 | 人工核实扫描结果后，项目状态才可设为 `verified` |
| 项目初始化 | `00-项目初始化.md` | 已核实的项目配置及前端 UI 规范 | 所有适用配置填写、用户确认后才能标记 `verified` |
| 需求发现 | `02-需求发现与候选池.md` | `requirements/pending/` 中的候选需求 | 用户批准候选需求；明确的版本生成指令按授权范围执行 |
| 需求入库 | `03-需求评审与TAPD入库.md` | 正式 TAPD 需求及真实 ID | 用户批准完整需求或已授权该版本入库，且 TAPD 创建成功 |
| 技术设计 | `04-技术设计与任务拆解.md` | 技术方案与任务清单 | 方案与拆解按授权范围审批；版本开发指令覆盖已批准需求内的常规实现，创建 TAPD 子任务另需明确授权 |
| 开发执行 | `05-开发执行.md` | 代码、测试及执行记录 | 本次代码修改已获授权 |
| 测试交付 | `06-测试与交付.md` | 测试报告、交付报告 | 审查、自测及合并闸门通过后执行已授权的 Git 操作；TAPD 状态和发布另按授权范围处理 |
| 模块自动化测试 | `07-模块自动化测试.md` | 按模块画像路由到 API 测试等 Agent；接口清单、用例、禅道 Bug 与测试报告 | 指令授权接口扫描、Apifox 上传回读、用例执行、可复现缺陷禅道入库及已确认目标通知；TAPD 缺陷和代码修复另按授权范围处理 |
| 原型与 UI | `08-原型与ArdotUI.md` | TAPD 原型、UI 图片、台账、Ardot 入项及通知 | 指令授权当前需求的 UI 交付；Ardot 与通知须回读成功 |

工作流文件位于 `workflows/`。各阶段使用的模板位于 `templates/`；审批要求以 `core/人工审批规范.md` 为准。

## 三、项目选择规则

项目注册信息以 `config/projects.yaml` 为准。每个项目必须有唯一且稳定的项目 ID。

如果当前任务没有明确指出项目，且工作空间中存在多个可能项目，必须先询问用户，不得根据目录名猜测。

写入文件前必须核对仓库根目录，避免把代码改到错误项目。

## 四、技术栈适配规则

项目通过 `stack_profiles` 引用技术栈配置。例如：

- `java_spring`：Java / Spring 后端。
- `vue_frontend`：Vue 前端。
- `harmonyos_arkts`：HarmonyOS / ArkTS。
- `python_backend`：Python 后端。
- `node_backend`：Node.js 后端。

技术栈配置提供扫描线索和编码约束，不代表项目一定使用某个版本或框架。版本、构建命令和实际依赖必须从仓库文件中核实。

## 五、项目隔离规则

- 不得混用不同项目的源码、业务规则、数据库结构、用户数据和执行记录。
- 共用目录只能存放通用工程方法，不得放置某个项目的专属业务知识。
- 默认只读取当前选定项目的配置和知识。
- 只有用户明确要求跨项目对比或联合测试时，才允许读取多个项目的资料。
- 不得将密钥、令牌、密码、证书或生产数据写入 `.ai`。

## 六、首次初始化

1. 先执行 `workflows/00-项目初始化.md`，只处理已确认的目标项目；不可读或不属于项目的 `.ai` 同级目录直接跳过。
2. 扫描架构和技术栈，在 `config/projects.yaml` 登记实际项目，并用 `projects/project.example.yaml` 建立配置。
3. 不能从仓库确定的必填项集中向用户询问，填完所有适用的 `.ai` 项目配置；不适用项写明理由。
4. 前端或客户端项目填写 `project-knowledge/<项目ID>/ui-guidelines.md`，参考 `templates/UI规范模板.md`。
5. 人工核对配置和画像后，才将项目状态改为 `verified`。
