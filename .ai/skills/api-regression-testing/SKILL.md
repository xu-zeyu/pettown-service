# API 模块自动化测试

用户说"进行 <模块> 的全量测试""跑一下 <模块> 接口测试"等，且路由判定为后端 HTTP 接口模块时，执行本闭环。该指令授权：读取仓库接口定义、将接口描述上传至已配置的 Apifox 项目、编写与执行测试用例、产出报告并发送已配置目标的企业微信通知。不授权：修改源代码、创建 TAPD 缺陷、变更数据库或生产环境操作；测试中发现缺陷需要入库时，按 `../../core/人工审批规范.md` 单独请求授权。

执行前先读取 `../../core/运行原则.md`、`../../core/人工审批规范.md`、`../../agents/测试Agent.md`、`../../workflows/07-模块自动化测试.md`、当前项目配置（`../../config/projects.yaml` → `../../projects/<项目>.yaml`）及 `../../project-knowledge/<项目>/modules.md`。多项目时，在用户明确的跨项目范围内分别核实各项目配置、仓库和模块地图；不能读取的项目列为受阻。

**执行顺序不可跳过：识别项目与接口 → 向用户确认每个项目的 Apifox ID（多项目）→ 逐项目上传并回读全部 API → 编写用例 → 执行 → 报告与通知。** 前一阶段受阻时，不启动后续阶段；可以先整理证据和缺口。

## 1. 模块与接口识别

1. 在用户指令中定位模块名，与 `modules.md` 的模块地图比对；匹配多个或没有匹配时先核实，不猜测模块边界。多项目时列出每个项目的稳定 ID、仓库路径、模块和关联依据，并确认本次测试范围。不要从相似名称推断关联。
2. 从仓库实际代码枚举该模块的接口：Spring 项目扫描 `@RestController`/`@RequestMapping` 及其方法级注解；能从运行中的服务或构建产物获取 Springdoc OpenAPI（`/v3/api-docs`）时优先使用。以仓库证据为准，不凭记忆补接口。
3. 产出接口清单：方法、路径、路径/查询/请求体参数、鉴权要求（如 Sa-Token）、所属 Controller。参数与响应结构使用代码中的真实类型（DTO/VO），不臆造字段。
4. 模块无 HTTP 接口或无法可靠识别时，停止并报告，退回路由。对异步事件或无 HTTP 入口的关联环节，保留其链路断言和证据，不伪造 API。

## 2. 上传 Apifox

1. 凭证从本 skill 同目录 `.env` 读取（见 `.env.example`）：`APIFOX_ACCESS_TOKEN`；单项目可用 `APIFOX_PROJECT_ID`，多项目用 `APIFOX_PROJECT_IDS_JSON` 记录“项目 ID → Apifox 项目 ID”。多项目时必须向用户逐一确认映射，已有配置也须确认；不使用 TAPD ID 或其他项目的 ID 代替。`.env` 不打印、不提交、不复制进报告。
2. 按项目分别将该项目接口清单组织为标准 OpenAPI 3 JSON。服务器地址取本项目已核实的测试环境配置；多项目可用 `API_BASE_URLS_JSON` 映射服务地址。调用每个 Apifox 项目的开放接口导入：
   `POST https://api.apifox.com/v1/projects/{projectId}/import-openapi`，请求头 `Authorization: Bearer <token>`、`X-Apifox-Api-Version: 2024-03-28`，body 为 `{"input": {"type": "openapi", "data": <OpenAPI JSON 字符串>}, "options": {"targetFolderId": <模块目录 ID, 可配 APIFOX_FOLDER_ID>}}`。
3. 每个项目导入后回读核对项目 ID、接口方法与路径、数量、目录及重复项；保存导入和回读证据。任一导入结果不明时先查询，不盲目重导。全部项目回读一致才算通过上传门禁。
4. Apifox 凭证、项目 ID、权限或开放接口不可用时，在 `.ai/runs/api-test/<日期>-<模块>/` 保存已识别接口清单和可生成的 OpenAPI 文件，记录受阻原因与人工导入指引；**停止本批用例编写和执行**。人工完成导入后仍须回读核对，方可继续。不得以本地 HTTP 测试代替上传。

## 3. 用例编写

1. 每个接口至少覆盖：正向用例、必填参数缺失、边界值、无效类型、未鉴权/无权限（适用时）。只编写能从代码或已确认业务规则推导断言的用例；不确定的预期结果标"待确认"，不编造断言。
2. 断言必须可执行：HTTP 状态码、响应 JSON 关键字段与类型、业务码；禁止"能调通就算过"。
3. 用例落地为 Apifox 测试场景/测试用例，或 Apifox CLI 可直接运行的集合；需要前置数据（登录态、依赖记录）时在准备步骤中显式构造并记录，不用生产数据。
4. 写/改接口的用例只在测试环境执行；单项目目标地址由 `.env` 的 `API_BASE_URL`、多项目由 `API_BASE_URLS_JSON` 决定，禁止指向生产地址，首次配置时执行前输出各项目环境供人工确认。
5. 多项目时先建立“关联链路清单”：每条列明业务目标、涉及项目和接口/事件、先后顺序、共享标识或数据映射、成功后的最终状态、规则来源。每条已确认且属于本次范围的链路至少有一个完整端到端正向用例，并覆盖已确认的关键失败/回滚/幂等场景。跨项目用例必须从上游实际响应或事件取值传给下游，检查中间状态与最终结果；不以各项目独立接口全绿替代链路测试。关键业务预期不明时向用户核实，不编造断言。

## 4. 执行

1. 全部项目上传并回读成功后，优先使用 Apifox CLI 执行单项目用例，例：`apifox run --access-token $APIFOX_ACCESS_TOKEN -t <测试用例/场景 ID> -e <环境 ID> -r cli,html --out-dir <报告目录>`；CLI 未安装时按 `npm i -g apifox-cli` 提示用户安装，不自动全局安装。
2. CLI 不可用或跨项目场景无法在单个 Apifox 项目中串联时，**在上传门禁通过后**可用 `scripts/run_cases.py`（或等效编排器）执行。用例以项目 ID 选择对应测试服务，并按顺序捕获上游值供下游请求使用；保留原始响应、关联 ID 和断言结果。该执行方式不免除上传门禁。
   `run_cases.py` 的用例集合需含 `apifox_uploads`，每个项目有真实回读得到的 `project_id`、`verified: true` 和证据路径；脚本会与 `.env` 的项目映射比对，回读真伪仍须执行者核实。多项目集合需列出 `required_flows`（本次范围内全部已确认链路名称）。`cases` 中每步用 `project` 选服务、`flow` 标记关联链路、`capture: {"变量名":"响应字段路径"}` 捕获上游值；后续路径、请求体和断言可引用 `${变量名}`。示例：上游用例 `capture: {"order_id":"data.id"}`，下游用例 `path: "/orders/${order_id}"`。回读字段及响应应以真实接口为准。
3. 记录每个用例的实际命令、退出码、响应摘要与失败原因。结果口径与工作流 06 一致：`通过`/`失败`/`未执行`/`受阻`，不得把未执行或受阻记为通过。
4. 有失败用例时完成全量执行并汇总，不中断后续用例；不为让结果变绿而修改接口或用例本身。

## 5. 报告与通知

1. 在 `.ai/runs/api-test/<日期>-<模块>/` 按项目保存接口清单、OpenAPI、Apifox 项目 ID 及上传回读证据；另存跨项目关联链路清单、用例集合、原始执行输出、`测试报告.md`（使用 `../../templates/测试报告模板.md`）。报告列出各项目环境和结果、链路总数及通过/失败/未执行/受阻数、每条链路的证据与失败原因、未确认规则，不记录凭证。
2. 执行完成或受阻后发送企业微信通知：复用 `../tapd-requirement-intake/scripts/send_wecom.py`，纯文本经标准输入传入。内容含项目与模块、环境、Apifox 上传状态、用例和关联链路各类结果数、失败摘要、报告路径。一次执行对同一目标只成功通知一次；按脚本返回的 HTTP 状态与业务码核对，结果不明先核查不重发。
3. 存在失败用例时，报告与通知如实列出；是否创建 TAPD 缺陷、是否触发修复，等待用户明确指令。

## 6. 闭环门禁

满足以下全部条件，本次模块测试才记为"已完成"：全部涉及项目的接口识别有仓库证据、各项目 Apifox 上传回读一致、全部已编写用例实际执行且结果如实记录、报告落盘、通知核对成功。多项目还须列清全部已确认的关联链路；只有这些链路的用例全部实际通过、没有未确认的关键业务规则，才可报告“本次范围内关联业务链路 100% 通过”。失败、未执行或受阻必须如实报告，不能以接口通过率替代链路通过率，也不对未识别的业务作 100% 保证。
