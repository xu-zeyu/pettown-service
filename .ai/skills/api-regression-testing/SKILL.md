# API 模块自动化测试

用户说"进行 <模块> 的全量测试""跑一下 <模块> 接口测试"等，且路由判定为后端 HTTP 接口模块时，执行本闭环。用户已明确要求本流程对可复现的真实缺陷通过禅道 MCP 入库并通知企业微信；测试任务授权仓库读取、Apifox 接口导入与回读、非生产环境用例编写执行、禅道 Bug 创建回读、已确认目标的通知。不授权修改项目业务源码、创建 TAPD 缺陷、变更数据库或生产环境操作。TAPD 事项仍按 `../../core/人工审批规范.md`。

执行前先读取 `../../core/运行原则.md`、`../../core/人工审批规范.md`、`../../agents/测试Agent.md`、`../../workflows/07-模块自动化测试.md`、当前项目配置（`../../config/projects.yaml` → `../../projects/<项目>.yaml`）及 `../../project-knowledge/<项目>/modules.md`。多项目时，在用户明确的跨项目范围内分别核实各项目配置、仓库和模块地图；不能读取的项目列为受阻。

**执行顺序不可跳过：识别服务与接口 → 确认每个 Apifox 目标映射 → 逐目标导入并回读全部 API → 编写红绿与对抗用例 → 执行 → 可复现缺陷入库禅道并回读 → 报告 → 企业微信通知。** 同一仓库的两个服务也可能对应两个 Apifox 项目，映射键用 `<稳定项目 ID>/<服务名>`；不要把同一项目的服务误判为跨仓库项目。前一阶段受阻时，不启动后续阶段；可以先整理证据和缺口。

## 1. 模块与接口识别

1. 在用户指令中定位模块名，与 `modules.md` 的模块地图比对；匹配多个或没有匹配时先核实，不猜测模块边界。多项目时列出每个项目的稳定 ID、仓库路径、模块和关联依据，并确认本次测试范围。不要从相似名称推断关联。
2. 从仓库实际代码枚举该模块的接口：Spring 项目扫描 `@RestController`/`@RequestMapping` 及其方法级注解；能从运行中的服务或构建产物获取 Springdoc OpenAPI（`/v3/api-docs`）时优先使用。以仓库证据为准，不凭记忆补接口。
3. 产出接口清单：方法、路径、路径/查询/请求体参数、鉴权要求（如 Sa-Token）、所属 Controller。参数与响应结构使用代码中的真实类型（DTO/VO），不臆造字段。
4. 模块无 HTTP 接口或无法可靠识别时，停止并报告，退回路由。对异步事件或无 HTTP 入口的关联环节，保留其链路断言和证据，不伪造 API。

## 2. 上传 Apifox

1. 凭证从本 skill 同目录 `.env` 读取（见 `.env.example`）：`APIFOX_ACCESS_TOKEN`；`APIFOX_PROJECT_IDS_JSON` 记录 `<稳定项目 ID>/<服务名> → Apifox 项目 ID`，单服务兼容 `APIFOX_PROJECT_ID`。逐目标向用户确认映射，已有配置也须核对；不使用 TAPD、禅道或其他服务的 ID 代替。`.env` 不打印、不提交、不复制进报告。
2. 先取得当前代码的完整 Springdoc OpenAPI 3 文档，逐项比对 Controller 的方法与路径。启动临时实例提取文档时使用隔离的测试配置和空闲端口，核对实际进程，避免读到 IDE 中旧服务的文档。服务器地址写入已确认的非生产测试地址，不把临时端口写成最终测试目标。
3. 用 `python3 .ai/skills/api-regression-testing/scripts/apifox_sync.py --target-key <项目/服务> --spec <openapi.json> --out-dir <证据目录>` 执行。脚本先只读调用官方 `export-openapi` 确认目标可读；缺少接口时调用一次 `POST /v1/projects/{projectId}/import-openapi`，`input` 为**完整 OpenAPI JSON 字符串**，不是 `{type,data}`；目录选项名称是 `targetEndpointFolderId`，不是 `targetFolderId`。目标已有全部预期接口时只回读不写；仅有部分预期接口时先核对覆盖策略与重复项，脚本禁止盲目混合导入。首次导入后再次 `export-openapi`，比较全部预期方法与路径。官方契约见 [导入](https://apifox-openapi.apifox.cn/api-173409873)、[导出](https://apifox-openapi.apifox.cn/api-173411997)。
4. 导出读回必须是 HTTP 200、非空 JSON、含 OpenAPI 3 `paths`；HTTP 201、空 HTML、超时或代理应答都不是入库成功。只在回读覆盖全部预期接口且项目映射正确时将 receipt 标记 `verified: true`。配置目录时还须用 Apifox `endpoint list/get` 或 UI 核对目录及重复项，脚本不会仅凭导出文件判定目录正确。导入响应不明只做只读核查，不自动重导。
5. 开放 API 不可用时，保存 OpenAPI、请求元数据和空响应证据；若 Apifox CLI 可用，按其当前 `import`、`endpoint list/get` 契约走官方 CLI，并同样回读。否则提供人工文件导入指引，导入后仍须回读。**全部目标核对成功之前停止用例编写和执行**，不得用本地 HTTP 测试代替上传。

## 3. 用例编写

1. 每个接口至少覆盖：正向用例、必填参数缺失、边界值、无效类型、未鉴权/无权限（适用时）。先用已确认契约做基线绿灯，再做能复现预期缺陷的红灯与权限、并发、幂等、回滚等相关对抗场景；修复后的绿灯复测须等用户授权修复且测试环境更新。只编写能从代码或已确认业务规则推导断言的用例；不确定的预期结果标"待确认"，不编造断言。
2. 断言必须可执行：HTTP 状态码、响应 JSON 关键字段与类型、业务码；禁止"能调通就算过"。
3. 用例落地为 Apifox 测试场景/测试用例，或 Apifox CLI 可直接运行的集合；需要前置数据（登录态、依赖记录）时在准备步骤中显式构造并记录，不用生产数据。
4. 写/改接口的用例只在测试环境执行；单项目目标地址由 `.env` 的 `API_BASE_URL`、多项目由 `API_BASE_URLS_JSON` 决定，禁止指向生产地址，首次配置时执行前输出各项目环境供人工确认。
5. 多项目时先建立“关联链路清单”：每条列明业务目标、涉及项目和接口/事件、先后顺序、共享标识或数据映射、成功后的最终状态、规则来源。每条已确认且属于本次范围的链路至少有一个完整端到端正向用例，并覆盖已确认的关键失败/回滚/幂等场景。跨项目用例必须从上游实际响应或事件取值传给下游，检查中间状态与最终结果；不以各项目独立接口全绿替代链路测试。关键业务预期不明时向用户核实，不编造断言。

## 4. 执行

1. 全部项目上传并回读成功后，优先使用 Apifox 官方 CLI 的测试场景运行能力；先核对本机 `apifox --help` 的当前参数与已确认的场景、环境 ID。令牌从环境或受保护配置读取，避免放进可见命令历史。CLI 未安装时提示安装，不自动全局安装。
2. CLI 不可用或跨项目场景无法在单个 Apifox 项目中串联时，**在上传门禁通过后**可用 `scripts/run_cases.py`（或等效编排器）执行。用例以项目 ID 选择对应测试服务，并按顺序捕获上游值供下游请求使用；保留原始响应、关联 ID 和断言结果。该执行方式不免除上传门禁。
   `run_cases.py` 的用例集合需含 `apifox_uploads`，每个目标指向 `apifox_sync.py` 生成的真实回读 receipt 与证据路径；脚本会与 `.env` 映射比对。多服务集合需列出 `required_flows`（本次范围内全部已确认链路名称）。`cases` 中每步用 `project` 选服务、`flow` 标记关联链路、`capture: {"变量名":"响应字段路径"}` 捕获上游值；后续路径、请求体和断言可引用 `${变量名}`。示例：上游用例 `capture: {"order_id":"data.id"}`，下游用例 `path: "/orders/${order_id}"`。回读字段及响应应以真实接口为准。
3. 记录每个用例的实际命令、退出码、响应摘要与失败原因。结果口径与工作流 06 一致：`通过`/`失败`/`未执行`/`受阻`，不得把未执行或受阻记为通过。
4. 有失败用例时完成全量执行并汇总，不中断后续用例；不为让结果变绿而修改接口或用例本身。

## 5. 禅道 Bug 入库（开源版 22.7）

1. 仅将**实际执行、可稳定复现、与已确认契约不符**的缺陷入库；环境故障、未确认规则、仅凭静态猜测的现象只写报告，不创建 Bug。同一根因的失败合并为一条，保留全部受影响接口和用例证据。不要为了凑覆盖率制造 Bug。
2. 先读取本目录 `.env` 的 `ZENTAO_PRODUCT_IDS_JSON`（或项目配置的 `zentao.product_id`），向用户核实稳定项目/服务到禅道**产品 ID** 的映射；禅道项目 ID、执行 ID、TAPD ID 和 Apifox ID 都不能代替 `productId`。`get_projects` 只列项目，不证明产品归属。无可核实产品 ID 时把缺陷列为“待入库”，请求用户给出产品 ID，不向相似名称产品写入。可选执行 ID、影响版本、指派人也只使用已确认值。
3. 使用已连接的 `zentao` MCP：先在可用的只读能力和本次台账中按产品、标题、失败签名查重；若连接器无法完整搜索产品 Bug，记录查重范围，必要时在禅道 UI 核对。调用 `create_bug(productId, title, steps, severity, pri, type, openedBuild...)`；`steps` 写明环境、基线提交、前置数据、请求与脱敏响应、期望/实际、复现次数及报告证据路径。不得放入令牌、密码或个人信息。
4. 创建后立即用 `get_bug_detail(bugId)` 回读产品 ID、标题、重现步骤和状态；仅回读一致才标为“已入库”并引用真实 Bug ID。响应超时或 ID 不明时只读核查，不盲目重建。禅道 22.7 的 API 行为以当前 MCP 实际工具契约和回读为准，不自行拼接未验证的 REST API 路径。不能使用 MCP 时标记入库受阻。
5. 已入库 Bug 先写报告，再按 `../wecom-notification/SKILL.md` 发企业微信缺陷通知。通知只包含真实 Bug ID、标题、严重级别、简短影响和报告路径；回读失败或待入库时不能宣称已入库。Bug 后续解决、关闭、指派变更不在本测试指令授权范围内。

## 6. 报告与通知

1. 在 `.ai/runs/api-test/<日期>-<模块>/` 按目标保存接口清单、OpenAPI、Apifox ID、导入及导出 receipt；另存关联链路清单、用例集合、原始执行输出、禅道 Bug 台账和 `测试报告.md`（使用本 skill 的 `templates/API测试报告模板.md`）。报告列出各环境和结果、链路总数及通过/失败/未执行/受阻数、每条链路的证据与失败原因、禅道已入库/待入库/受阻数、未确认规则，不记录凭证。
2. 执行完成或受阻后加载 `../wecom-notification/SKILL.md`，使用共享发送脚本向已核实群发送测试结果。内容含项目与模块、环境、Apifox 上传状态、用例和关联链路各类结果数、禅道 Bug 真实 ID 与待入库数、失败摘要、报告路径。真实 Bug 入库并回读后可另发一次缺陷通知；事件键不同，均须去重、核对 HTTP 和业务码。目标群不明或自动审批拒绝时保留草稿，不绕过。
3. 失败用例如实列出；是否创建 TAPD 缺陷、是否触发修复，等待用户明确指令。

## 7. 闭环与商用验收门禁

满足以下全部条件，本次模块测试才记为"已完成"：全部目标接口有仓库证据、Apifox 按目标真实入库且回读一致、必需用例实际执行且结果如实记录、可复现缺陷按已确认禅道产品入库回读或明确列出受阻原因、报告落盘、通知核对成功。多服务还须列清并执行全部已确认关联链路。只有范围内必需用例及关键链路全部实际通过、无未解决阻断缺陷、无未确认关键业务规则和未执行必需项，才可报告“本次范围达到商用验收门禁”。即使达到门禁，也只对已定义的范围与环境负责，不能承诺软件在所有场景下绝对无缺陷或“100% 可商用”。
