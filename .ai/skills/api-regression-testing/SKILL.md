# API 模块自动化测试

用户说"进行 <模块> 的全量测试""跑一下 <模块> 接口测试"等，且路由判定为后端 HTTP 接口模块时，执行本闭环。该指令授权：读取仓库接口定义、将接口描述上传至已配置的 Apifox 项目、编写与执行测试用例、产出报告并发送已配置目标的企业微信通知。不授权：修改源代码、创建 TAPD 缺陷、变更数据库或生产环境操作；测试中发现缺陷需要入库时，按 `../../core/人工审批规范.md` 单独请求授权。

执行前先读取 `../../core/运行原则.md`、`../../core/人工审批规范.md`、`../../workflows/07-模块自动化测试.md`、当前项目配置（`../../config/projects.yaml` → `../../projects/<项目>.yaml`）及 `../../project-knowledge/<项目>/modules.md`。

## 1. 模块与接口识别

1. 在用户指令中定位模块名，与 `modules.md` 的模块地图比对；匹配多个或没有匹配时先核实，不猜测模块边界。
2. 从仓库实际代码枚举该模块的接口：Spring 项目扫描 `@RestController`/`@RequestMapping` 及其方法级注解；能从运行中的服务或构建产物获取 Springdoc OpenAPI（`/v3/api-docs`）时优先使用。以仓库证据为准，不凭记忆补接口。
3. 产出接口清单：方法、路径、路径/查询/请求体参数、鉴权要求（如 Sa-Token）、所属 Controller。参数与响应结构使用代码中的真实类型（DTO/VO），不臆造字段。
4. 模块无 HTTP 接口或无法可靠识别时，停止并报告，退回路由。

## 2. 上传 Apifox

1. 凭证从本 skill 同目录 `.env` 读取（见 `.env.example`）：`APIFOX_ACCESS_TOKEN`、`APIFOX_PROJECT_ID`。`.env` 是本机凭证文件，不打印、不提交、不复制进报告。
2. 将接口清单组织为标准 OpenAPI 3 JSON（服务器地址取自 `.env` 的 `API_BASE_URL` 或项目配置），调用 Apifox 开放接口导入：
   `POST https://api.apifox.com/v1/projects/{projectId}/import-openapi`，请求头 `Authorization: Bearer <token>`、`X-Apifox-Api-Version: 2024-03-28`，body 为 `{"input": {"type": "openapi", "data": <OpenAPI JSON 字符串>}, "options": {"targetFolderId": <模块目录 ID, 可配 APIFOX_FOLDER_ID>}}`。
3. 导入后回读核对：通过 Apifox 项目内查询或重新导出比对接口数量与路径，确认无遗漏、无重复。导入结果不明时先查询，不盲目重导导致重复。
4. Apifox 开放接口不可用或未配置凭证时，降级为：在 `.ai/runs/api-test/<日期>-<模块>/` 产出 `openapi.json` 并给出人工导入指引，后续步骤改用本地可执行用例（见第 4 节降级路径），并在报告中标注"Apifox 上传未执行"。

## 3. 用例编写

1. 每个接口至少覆盖：正向用例、必填参数缺失、边界值、无效类型、未鉴权/无权限（适用时）。只编写能从代码或已确认业务规则推导断言的用例；不确定的预期结果标"待确认"，不编造断言。
2. 断言必须可执行：HTTP 状态码、响应 JSON 关键字段与类型、业务码；禁止"能调通就算过"。
3. 用例落地为 Apifox 测试场景/测试用例，或 Apifox CLI 可直接运行的集合；需要前置数据（登录态、依赖记录）时在准备步骤中显式构造并记录，不用生产数据。
4. 写/改接口的用例只在测试环境执行；目标环境由 `.env` 的 `API_BASE_URL` 决定，禁止指向生产地址，执行前输出环境供人工确认（首次配置时）。

## 4. 执行

1. 已上传 Apifox：使用 Apifox CLI 执行，例：`apifox run --access-token $APIFOX_ACCESS_TOKEN -t <测试用例/场景 ID> -e <环境 ID> -r cli,html --out-dir <报告目录>`；CLI 未安装时按 `npm i -g apifox-cli` 提示用户安装，不自动全局安装。
2. 降级路径：用 `scripts/run_cases.py`（或等效脚本）以 HTTP 客户端按用例集合逐个请求并断言，输出 JSON 结果。
3. 记录每个用例的实际命令、退出码、响应摘要与失败原因。结果口径与工作流 06 一致：`通过`/`失败`/`未执行`/`受阻`，不得把未执行或受阻记为通过。
4. 有失败用例时完成全量执行并汇总，不中断后续用例；不为让结果变绿而修改接口或用例本身。

## 5. 报告与通知

1. 在 `.ai/runs/api-test/<日期>-<模块>/` 保存：接口清单、openapi.json（如生成）、用例集合、原始执行输出、`测试报告.md`（使用 `../../templates/测试报告模板.md`，写明环境、总数、通过/失败/未执行/受阻、失败明细与证据链接）。
2. 执行完成后发送企业微信通知：复用 `../tapd-requirement-intake/scripts/send_wecom.py`，纯文本经标准输入传入。内容含模块、环境、用例总数与各类结果数、失败接口列表（路径+原因摘要）、报告路径。一次执行对同一目标只成功通知一次；按脚本返回的 HTTP 状态与业务码核对，结果不明先核查不重发。
3. 存在失败用例时，报告与通知如实列出；是否创建 TAPD 缺陷、是否触发修复，等待用户明确指令。

## 6. 闭环门禁

满足以下全部条件，本次模块测试才记为"已完成"：接口识别有仓库证据、Apifox 上传回读一致（或已明确标注降级）、全部已编写用例实际执行且结果如实记录、报告落盘、通知核对成功。任一项未满足，状态记为对应缺口（如"通知待核实"），不宣称闭环完成。
