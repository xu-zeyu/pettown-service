# 企业微信群通知

本 skill 只负责通知。调用方必须先完成自己的业务门禁（例如 TAPD 入库回读、代码合并回读、Apifox 上传回读、禅道 Bug 回读），再交付明确的事件、目标和消息。用户授权对应流程的通知时可执行；自动审批审查拒绝时保留草稿并向用户说明原因，不换工具或间接绕过。

## 固定目标与配置

1. 复用研发流程已使用的 `.ai/skills/tapd-requirement-intake/.env`。该文件必须同时有 `WECOM_WEBHOOK_URL` 与 `WECOM_TARGET_NAME`；后者是用户确认的实际群名，不能从 webhook key 推断。没有群名、群名与本次预期不符或目标不明时停止发送并请用户确认。
2. 将纯文本通过标准输入传给 `python3 .ai/skills/wecom-notification/scripts/send_wecom.py`；不要把 URL、密钥或消息放在命令行参数。旧入口 `tapd-requirement-intake/scripts/send_wecom.py` 是兼容转发，仍调用同一实现。
3. 消息只包含接收者完成本事件所需信息：项目、事件、真实记录 ID/链接、结果、失败或受阻原因和报告路径。测试通知区分 Apifox 上传、用例、链路与禅道 Bug 入库状态；不发送令牌、验证码、原始响应、用户数据或其他无关内部资料。

## 回执与去重

- 发送前在运行目录记下 `目标群 + 事件类型 + 业务 ID/运行 ID`，并检查该键是否已有成功回执。成功通知只发一次。
- 脚本仅在 HTTP 200 且企业微信 JSON `errcode=0` 时返回 `sent`。保存脱敏的返回状态、业务码和时间；脚本不会打印 webhook。
- 网络超时、空响应或无法确定结果时记为 `delivery_uncertain`，先到目标群或机器人后台核查，不能盲目重发。被拒绝或配置缺失记为受阻，保留通知草稿。

## 调用方时机

- 需求入库：TAPD 创建、负责人和链接回读后发送创建通知。
- 版本研发：当前项开始前发开始通知，合并与已授权的 TAPD 状态回读后发完成通知。
- API 测试：测试结束或受阻后发测试结果；发现可复现 Bug 时，禅道 Agent 的官方 API V2 创建与详情回读成功后再发带真实 Bug ID 的缺陷通知。若禅道入库受阻，说明待入库，不能写成已入库。
- UI：Ardot 图片入项及回读完成后发送。
