# TAPD 版本研发交付

用户说“开始 <版本> 代码编写”“开发 <版本> 需求”等，即启动该版本的研发流程。先读取 `../../agents/研发Agent.md`、`../../workflows/04-技术设计与任务拆解.md`、`../../workflows/05-开发执行.md`、`../../workflows/06-测试与交付.md` 和 `../../core/人工审批规范.md`。该指令授权此版本内常规代码修改、逐项提交与合并、开始/完成通知；范围变更、发布、部署及高风险操作仍按审批规范处理。不要把配置本 skill 当成开始某版本开发。

1. 从 TAPD 实时核对版本或迭代的所属空间及记录。若版本不是 TAPD 中的字段，依据已核实的版本需求池与各真实 TAPD ID 核对，不靠标题猜测归属。只纳入已批准、可验收且属于目标仓库的事项；跨仓库事项分别列出，不在本仓库实施。记录 TAPD 链接、标题、状态、原始优先级、映射后的 P 级、依赖与验收标准。映射依据须来自已批准需求池或 TAPD 字段；未知优先级标待确认，不臆造 P 值。
2. 以 `../../templates/版本开发清单模板.md` 在 `.ai/runs/<版本>/` 生成版本清单，按 P0→P1→P2→P3 排序；同级按已确认依赖排拓扑顺序，再按真实 TAPD ID 固定顺序。依赖若要求低优先级先行，在清单中注明原因并调整。暂缓项不进入执行序列。每条清单对应一个可独立审查与合并的交付单元、一个分支；若一个 TAPD 需求无法独立交付，先拆为可验收子项并保留父 ID 关联。不可确认的范围或依赖先澄清。清单与执行记录须留在协调工作区，不能混入各项功能分支的代码差异。
3. 严格串行：当前项的开始通知成功后，才从最新目标分支创建该项的新分支；完成设计、代码、红绿与对抗自测、构建、逐文件代码审查、问题修复与复审、交付记录及合并回读后，按已获授权的目标同步 TAPD 状态并回读，再发送完成通知，最后才开始下一项。不得并行开发或提前创建后续项分支。工作区有无关改动时先可靠隔离；不能隔离则停在当前项。
4. 分支名使用 `feat/<版本>-<TAPD_ID>-<简短主题>`（缺陷可用 `fix/`；同一需求拆成多项时增加清单序号以保持唯一）；记录基线与目标分支。每项先映射验收标准和设计，再按工作流 05/06 编码、自测、审查。优先取得独立审查；不可用时明确记录结构化自审。所有必需检查通过、审查无未解决问题、差异仅含当前项，才提交并合并。合并后核对目标分支含该项提交与测试证据；失败、冲突、测试受阻或审查未通过则保留分支，记录阻碍，不启动下一项。
5. TAPD 状态同步是完成闸门：开始实施前核对项目工作流状态图和用户授权的目标状态；合并回读后重新读取当前记录，按允许的下一状态逐步流转，每步回读 ID、空间、标题和状态。只流转到已有证据支持的阶段，不为到达终态而虚构产品体验、测试或发布结果；未获授权或目标阶段不可达时，记录具体阻碍并停在最后已核实状态，不将该项标为已完成，也不开始下一项。写入超时或结果不明时先查询，避免重复流转。
6. 通知使用已配置的企业微信群机器人 `../tapd-requirement-intake/scripts/send_wecom.py`，从标准输入传纯文本。开始通知包含版本、序号、TAPD ID/链接、优先级、标题、分支、计划范围与验收点；完成通知包含提交/合并结果、审查与测试实际结果、TAPD 回读后的状态、残余风险和链接。只发送当前项必要信息，不泄露密钥。每次按脚本返回的 HTTP 状态与业务码记录结果；同一项、事件、目标已成功通知时不重发，结果不明时先核查，不盲目重试。完成通知仅在合并及 TAPD 状态核对成功后发送。通知失败或不明确时记录状态并暂停该项后续动作。
7. 每项更新清单状态与执行证据，区分未开始、进行中、受阻、已合并但 TAPD 待核实、已合并但通知待核实、已完成。TAPD 状态只在用户指令授权且项目状态流转已核实时更新；代码合并本身不意味着自动关闭 TAPD。最终报告逐项列出真实 ID、分支、审查、测试、合并、TAPD 状态回读和通知结果。

“生成 <版本> 版本需求”由 `../tapd-requirement-intake/SKILL.md` 处理，按工作流 02/03 完成需求池、评审、TAPD 入库、回读与创建通知；此指令本身不启动代码开发。
