# TAPD 需求池入库

用户说“生成 <版本> 版本需求”等，即授权该版本需求池整理、评审、TAPD 入库、回读与已配置目标的创建通知；按 `../../core/人工审批规范.md` 执行，不重复索取同一范围的批准。该指令不授权代码开发，也不允许自行确定未确认的业务规则。必要时先读取 `../../agents/研发Agent.md` 与工作流 02/03。

1. 核对目标仓库、产品范围、TAPD 工作空间名称与 ID。读取现有需求的标题、状态和必要描述，合并重复项；不要用本地项目配置代替 TAPD 实时核对。
2. 从用户目标、仓库现状和可引用的竞品资料形成需求。每项写明场景、范围、验收标准、依赖、权限/数据影响与待确认规则。竞品功能只是候选，不自动成为产品事实。每次版本需求池必须有去重后至少 20 条独立、属于本版本、有来源且可验收的合格需求。
3. 让主张方说明价值，让质疑方检查复用现有能力、人工替代、成本、风险和业务前提。价值 V、紧急度 U、可行性 F、战略匹配 S 各打 1–10 分；`Score = round((0.4V + 0.3U + 0.2F + 0.1S) * 10)`。建议 85–100 为 P0、75–84 为 P1；低于 75 分暂缓，不计入合格需求池。评分与优先级均写明依据，不为凑数抬分。
4. 入库前确认合格需求不少于 20 条，且每条评分不低于 75 分；重复、超范围、缺少可验收描述或关键业务规则未确认的条目不计数。数量不足时继续搜集证据；仍不足则记录实际条数和缺口，标记本批次未达标，不启动入库和通知，也不编造或人为拆分需求。达标且用户已授权正式入库后，按已核实空间和标题逐项创建 TAPD 需求。负责人默认使用当前项目配置的 `tapd.default_owner`（`pet-system` 为徐泽宇），单条有用户明确指定时覆盖；写入前实时查询项目成员，确认唯一匹配并使用工具要求的标识，查不到或歧义时暂停该条入库。创建前查重；响应不明确时先按标题查询，勿直接重试。其他字段只设置已核实的候选值，不猜测迭代或版本字段。若用户只要求本地需求池，不写 TAPD。
5. 每条创建后回读 ID、标题、描述、优先级、创建时间、负责人和链接，核对负责人是否与预期一致。记录真实回执；未回读成功或负责人不一致的条目不得宣称入库完成。
6. 用户授权通知后，使用本 skill 的固定企业微信机器人目标：`scripts/send_wecom.py` 从同目录的 `.env` 读取 `WECOM_WEBHOOK_URL`。用户已明确指定该 Webhook 为通知目标，无需每次索取地址或再次确认目标；若本次任务要求其他群，先核对新目标。只在 TAPD 创建并回读成功后发送，通知只包含必要业务信息、TAPD 真实 ID 与链接，不包含密钥、验证码或无关内部信息。用脚本的 HTTP 状态和企业微信业务返回码核对结果；结果不明确时核查，勿盲目重发；同一需求对同一目标只成功通知一次。
7. 产出版本需求池与执行记录，列出合格需求总数、各条评分与依据、实际入库数，并区分已入库、未入库、已通知和未通知。关联来源及日期；若入库或回读失败导致实际完成数不足 20 条，报告未完成，不编造结果。

当前项目的产品与 TAPD 空间以 `../../projects/pet-system.yaml` 和实时查询共同确定；流程细节见 `.ai/workflows/03-需求评审与TAPD入库.md`。用户对本次入库和通知的明确指令已构成相应授权，不重复请求批准。

通知时将工作流格式化后的纯文本通过标准输入传给 `python3 .ai/skills/tapd-requirement-intake/scripts/send_wecom.py`。`.env` 是本机凭证文件，不要打印、提交或复制到需求记录；更换机器人时更新该文件。
