## 一、需求背景与现状

### 1.1 仓库事实（代码可见范围，不代表已验收）

> 【2026-11-05 复核结论】以下事实已于今日重新核实，无变化：`docs/sql` 目录仍不存在（`ls docs/sql` 报 No such file or directory，R1 仍成立）；`Pet.java` 仍仅含 `id/name/species` 三字段（R2/R3 依据仍成立）；当前 Git 分支为 `main`，工作区仅有 `.ai`、`.workbuddy` 文档类未提交变更，无源码改动。

本项目为「宠物管理系统」后端服务 `pettown-server`，基于 Java 17 / Spring Boot 3.5.16 / MyBatis-Plus 3.5.15 / Sa-Token 1.44.0 / Springdoc OpenAPI，运行时依赖 MySQL 与 Redis，测试使用 H2。按 `settings.gradle.kts` 划分为 7 个 `pettown-common` 公共模块、4 个 `pettown-modules` 业务模块、3 个 `pettown-boot` 启动应用。

三个启动入口及其当前能力：

| 启动应用 | 端口 | 接口前缀 | 已实现能力（源码可见） |
|---|---|---|---|
| `pettown-boot/app` | 8080 | `/api/pets/**` | 宠物创建、详情、列表 |
| `pettown-boot/miniapp` | 8082 | `/api/miniapp/**` | 登录（手机号+密码+验证码，首次自动注册）、验证码、当前用户 |
| `pettown-boot/admin` | 8081 | `/mng/**` | 管理员登录（双因子）、账号 / 角色 / 权限管理（14 个内置权限码） |

### 1.2 本周已完成的背景工作（来自工作日志，2026-11-04）

- 管理端权限功能已实现：对齐 `admin_account / admin_role / admin_permission / admin_role_permission` 四表模型，账号采用单角色 `role_id` 绑定；测试契约全绿（AdminAlignmentTests 15 + AdminMigrationTests 2 + AdminSingleRoleMigrationTests 3 + AdminOpenApiTests 2，module-business 25 个测试全绿）。
- 登录与接口轨道已收敛：登录统一 `/auth/login`、个人信息统一 `/auth/me`、验证码 `/auth/verification`；移除 `/login/sms`、`/public/captcha/login/{name}`、`/self`、`/info`、`createRole` 等重复轨道，OpenAPI 操作数 45 → 40。

### 1.3 驱动本周需求的现实缺口

1. **宠物业务极薄**：`Pet` 实体仅含 `id / name / species` 三个字段，无主人归属、无图片、无品种 / 性别 / 年龄 / 生日等档案信息，且 `getPet` / `listPets` 仅要求登录、**不校验数据归属**（见 §8 越权风险）。
2. **三端能力不对齐**：App 端有宠物接口，小程序端仅有登录 / 用户，无宠物能力；管理端无宠物管理入口。
3. **基础设施配置已就绪但业务未落地**：miniapp 配置了阿里云 OSS、RabbitMQ、Spring Cloud Config、外部 Python 服务、multipart 文件上传（20MB），但仓库中未见对应业务代码；`common-file` 的 OSS 服务为「部分实现」、未接入任一启动应用。
4. **工程质量阻塞项**：`pettown-boot/admin/build.gradle.kts` 的 `processTestResources` 引用 `docs/sql/admin.sql` 等 4 个脚本，仓库中未找到 `docs/sql`，可能阻塞管理端测试资源处理（未执行构建验证）。

## 三、核心功能描述（本周候选需求）

> 每条均按 `templates/需求模板.md` 组织关键要素；编号仅供引用，不作为 TAPD ID。

### 需求 R1（P0）— 修复管理端测试资源缺失，恢复可构建基线
- **类型**：工程质量阻塞项 / 缺陷修复。
- **期望行为**：`./gradlew build`（含 `processTestResources`）在管理端可正常通过；`docs/sql/admin.sql`、`admin-single-role.sql`、`admin-reference-alignment.sql`、`admin-test-data.sql` 四个脚本在仓库中存在且与 `schema.sql` 契约一致，测试数据种子过程可执行。
- **数据与接口影响**：不改变对外 API 契约；仅影响测试资源路径与 SQL 脚本落位。
- **验收标准**：见 §5 R1。

### 需求 R2（P0）— 明确宠物数据归属与越权防护
- **类型**：安全 / 数据隔离。
- **期望行为**：明确 `Pet` 是否归属某用户；若归属，则 `getPet(id)`、`listPets()` 必须限定为当前登录用户可访问的数据范围，并对跨用户访问返回统一错误码。
- **业务规则**：若采用「宠物归属用户」模型，需在 `Pet` 增加归属字段并回填既有数据策略；若产品确认「宠物为全局共享」，则需显式记录该决策并关闭本风险项。
- **数据与接口影响**：可能新增 `Pet` 归属字段、调整查询条件（`LambdaQueryWrapper` 增加归属过滤）。
- **权限与安全影响**：涉及数据隔离与授权逻辑变更，按规范需人工审批后方可实施。

### 需求 R3（P1）— 宠物档案字段完善
- **类型**：产品功能扩展。
- **期望行为**：在现有 `name / species` 基础上，补充宠物档案字段（候选：品种、性别、年龄 / 生日、头像图片、备注等【待确认具体清单】），并保持现有创建 / 详情 / 列表接口兼容。
- **业务规则**：新增字段需约定必填 / 选填、枚举取值（如性别、品种字典）与默认值；`createPet` 现有 `name/species` 语义不变。
- **数据与接口影响**：`Pet` 实体与 `CreatePetRequest` / `PetResponse` 同步扩展；可能需要数据库迁移脚本（需审批）。
- **验收标准**：见 §5 R3。

### 需求 R4（P1）— 文件上传能力落地（接入 common-file OSS）
- **类型**：基础设施补全。
- **期望行为**：将 `common-file` 中「部分实现」的 OSS 文件服务接入到需要图片 / 文件的端（优先小程序），打通上传 → 返回可访问 URL 的闭环；头像 / 宠物图片可引用该能力。
- **业务规则**：上传需校验文件类型与大小（miniapp 已配 20MB 上限【仓库事实】）；返回 URL 需区分内网 / 公网访问【待确认】。
- **数据与接口影响**：新增上传接口（沿用 miniapp 已配置的 `aliyun.oss` 凭证变量）。
- **依赖**：R3（宠物头像字段）依赖本项，但本项可独立交付。

### 需求 R5（P1）— 小程序端宠物能力补齐
- **类型**：能力对齐。
- **期望行为**：小程序端复用 `module-business` 的 `PetService`，补齐与 App 端一致的宠物创建 / 详情 / 列表接口，使小程序用户可管理宠物。
- **业务规则**：与 R2 归属模型保持一致；接口前缀沿用 `/api/miniapp/**`，遵循现有 Controller/DTO/VO 分层。
- **数据与接口影响**：`module-miniapp` 新增宠物 Controller 与请求 / 响应对象，复用 `PetService`。

### 需求 R6（P2）— 外部依赖业务场景澄清（RabbitMQ / Python 服务 / 配置中心）
- **类型**：产品 / 技术澄清（非纯编码）。
- **期望行为**：明确 miniapp 已配置的 RabbitMQ（消息队列）、`pythonService.api`（`http://192.168.7.51:8080/api/v1/repos`）、Spring Cloud Config 对应的真实业务场景，避免「配置存在但功能缺失」的隐性技术债。

### 需求 R7（P2）— 前端项目登记与联调

- **期望行为**：将管理端前端（工作日志提及 `jinHan-shop-admin-web`）登记为独立项目或明确归属；对已收敛的 `/auth/login`、`/auth/me`、账号 / 角色 / 权限接口做前后端联调确认。

## 六、业务规则与边界（汇总）

- 统一结果封装 `Result`、统一错误码 `ErrorCodeEnum`、统一日志切面 `@Log`、统一用户来源识别 `UserSourceResolver` 必须沿用（【仓库事实】）。
- 认证统一走 Sa-Token（`Bearer`，`Authorization` 头）；管理端为双因子登录（密码 + 短信验证码），验证码 key 格式 `pettown:verification-code:admin_login:<phone>`。
- 权限码语义不可随意改动：`AdminPermissionCodes` 与 14 个内置权限目录属数据库种子契约，即使无接口使用也保留。
- 新增任何接口、数据表、权限、认证逻辑均须先人工审批（见 `.ai/core/人工审批规范.md`）。

## 九、风险与依赖

1. **越权风险（R2）**：当前宠物接口无归属校验，多用户场景下存在数据泄露面，属本周期最高优先级安全风险。
2. **构建阻塞（R1）**：`docs/sql` 缺失可能使管理端测试资源处理失败；未实际执行 `build` 前结论为「静态核对」，需构建确认。
3. **配置-代码漂移（R6）**：miniapp 存在大量「已配置、未实现」的依赖（OSS/RabbitMQ/配置中心/Python 服务），长期会误导容量与安全评估。
4. **事实边界**：本文所有「待确认」项均不得由 AI 自行拍板，须产品 / 用户确认后定稿。
5. **审批依赖**：R2 涉及数据隔离与授权逻辑、R3/R4 涉及数据库变更，均须人工审批后实施。
