# 研发 Agent

本文件是代码需求的执行入口。进入开发前先完成上下文读取；每个需求使用独立 Git 分支；代码审查和红绿对抗自测全部通过后才允许合并。具体步骤见 `../workflows/05-开发执行.md` 与 `../workflows/06-测试与交付.md`。

## 1. 接收需求与读取上下文

1. 确认需求范围、验收标准、目标项目和仓库路径；已有 TAPD 需求时核对真实 ID，没有时记录可追溯的本地需求标识，不得编造 ID。
2. **编写任何代码前**，按顺序读取 `../README.md`、`../config/workspace.yaml`、`../config/projects.yaml`、注册表为当前项目指定的项目配置，以及适用的 `../config/stack-profiles/` 配置。
3. 读取 `../core/运行原则.md`、`../core/人工审批规范.md`、本文件、相关工作流，以及当前项目的 `../project-knowledge/<项目 ID>/architecture.md`、`modules.md`、`known-risks.md`。不存在的文件要记录缺口，再从仓库核实，不能按猜测补全。
4. 从实际仓库核对架构、构建配置、依赖、入口、相关源码与测试，并查找适用的 `AGENTS.md`、项目约束和已有差异。项目知识是线索，冲突时以当前仓库证据为准。
5. 向用户简要说明确认的架构、配置、约束、预计修改范围和验证命令。需求或仓库身份不清楚时先澄清。

## 2. 分支与开发

1. 修改代码前检查 `git status`、当前分支、目标分支和已有未提交变更。**每个需求单独创建一个功能分支**，不得在默认分支直接开发，也不得把多个需求混在同一分支。
2. 若工作区已有无关改动，先隔离本需求的变更，保留他人改动；不能可靠隔离时停止修改并说明阻碍。分支名包含需求标识和简短主题，执行记录写明基线提交。
3. 按需求验收标准编写或更新测试，先验证测试因目标行为尚未实现而失败（红灯），再实现最小完整变更并让测试通过（绿灯）。修复缺陷时，红灯测试应能复现缺陷。
4. 补充对抗自测：针对边界值、无效输入、权限或并发等与变更相关的风险设计反例，并执行回归测试。对不适用的维度说明原因；不把未运行的检查记为通过。

## 3. 审查与合并闸门

1. 开发完成后必须进行代码审查。优先由非作者审查；无法取得独立审查时执行逐文件结构化自审并明确标注。检查需求覆盖、架构约束、兼容性、安全、无关改动和测试质量；发现问题须修复并复审。
2. 记录红灯失败证据、绿灯结果、对抗自测结果、代码审查结论和实际命令。执行项目配置及仓库确认的相关测试与构建。
3. **只有全部相关测试为绿、对抗自测通过、代码审查无未解决问题，且变更范围已核对，才允许合并分支。** 任何失败、受阻或未执行的必需项都阻止合并；先修复并重测，或保留分支并报告阻碍。
4. Git 提交、推送、合并和发布遵循 `../core/人工审批规范.md`；已有明确授权可直接执行授权范围内的操作。合并后核对目标分支状态并记录合并结果。

文档或配置变更也要执行对应的红绿验证与审查；若不适合运行应用测试，使用能实际验证该变更的检查，并如实说明未运行的测试。
