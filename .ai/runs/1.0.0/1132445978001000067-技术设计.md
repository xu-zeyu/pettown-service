# 技术设计：1132445978001000067 — 移动端短信验证码发送

- 项目 ID：`pet-system`
- TAPD：[1132445978001000067](https://www.tapd.cn/32445978/prong/stories/view/1132445978001000067)
- 设计状态：用户已修订首项交付方式（Redis 人工取码）；真实短信投递留待后续
- 编写日期：2026-11-05

## 一、需求摘要

小程序匿名用户请求登录验证码。用户于 2026-11-05 指定暂只写入 Redis，由其自行读取；响应明确未发送短信。验证码 5 分钟有效且一次性消费；同一手机号 60 秒一次、每天至多 10 次，同一来源 IP 每天至多 50 次；非法手机号不写入 Redis。

## 二、现有实现分析

`VerificationCodeController` 当前开放 `POST /api/miniapp/verification/code`，仅调用 `VerificationCodeService.generate` 后返回成功。`VerificationCodeServiceImpl` 将六位明文验证码以用途和手机号为键缓存 5 分钟，`compareAndDelete` 可一次性消费。当前无短信投递和限流。`Cache` 接口无原子计数，但启动模块已接入 Redisson。现有 `/code` 接口若继续开放，会绕过新发送限流。

## 三、建议技术方案

1. `POST /api/miniapp/verification/send` 先校验手机号和用途，再以 Redis 原子操作检查并计入手机号 60 秒、手机号当日、来源 IP 当日额度；并发请求不能超额。按 Asia/Shanghai 日界计算日额度。Redis 不可用时拒绝请求。
2. 通过现有验证码服务生成并缓存六位码，五分钟后自动过期；沿用原子消费。`/send` 只返回“已写入 Redis，未发送短信”，不返回验证码。日志不得包含完整验证码。旧 `/code` 共用相同限流与语义。
3. 暂不接入短信供应商。真实投递、失败回滚和费用控制不计入本次完成范围，并在交付报告中明确与原 TAPD 验收差异。

## 四、影响模块与文件

- `module-miniapp`：验证码 Controller、Redis 限流器、可信代理地址解析与接口测试。
- `module-business`：验证码服务与短信适配；服务及并发/失败测试。
- `common-core` / `common-redis`：若原子计数能力需共用，扩展现有缓存接口和实现；不引入新存储。
- `pettown-boot/miniapp`：仅加入供应商所需配置，不写入凭证。

## 五、接口与数据模型变更

新增 `POST /api/miniapp/verification/send`，保留现有请求体字段；`/code` 兼容转发同一处理，防止限流旁路。无数据库结构变更。

## 六、权限与安全考虑

接口匿名访问，必须先校验手机号；验证码不得出现在响应或日志中。用户要求从 Redis 直接取码，因此 Redis 暂存六位码且五分钟过期；Redis 访问必须限制为可信运维/开发人员。默认使用 TCP 来源地址并忽略客户端 Forwarded 头；反向代理部署时配置可信代理直连 IP，由代理覆盖 `X-Real-IP`。验证码用途隔离；限额操作需原子化。

## 七、兼容性与数据迁移

无数据迁移。现有 `/code` 调用方尚未确认，切换策略需按客户端情况决定。

## 八、异常处理与可观测性

区分非法参数、限流、供应商拒绝、结果不明；监控发送受理与失败次数，不记录完整手机号或验证码。

## 九、测试策略

先写接口与服务红灯测试：非法手机号不写入、60 秒限额、日限额、一次性消费、并发限额、旧入口不能绕过、响应明确未发送短信。实现后运行相同测试和 `./gradlew :pettown-boot:miniapp:test :module-business:test`，再做相关构建与自审。

## 十、回滚方案

仅在已批准的兼容策略内恢复旧接口路由；回滚供应商配置及代码提交。保持服务端不会返回验证码。

## 十一、备选方案

真实短信服务后续单独接入。当前 Redis 人工取码仅用于用户指定的过渡阶段，不能在交付报告中称为“短信已发送”。

## 十二、假设与待确认问题
