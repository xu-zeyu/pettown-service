## TAPD 要求与仓库现状

TAPD 要求 `GET /api/admin/users`（按手机号、注册来源筛选并分页）、`GET /api/admin/users/{id}`、`PUT /api/admin/users/{id}/status`（封禁/解封）；封禁后小程序 Token 失效且登录被拒。需要 `user_account.status` 和 `biz:user:read`、`biz:user:status` 权限。记录中“封禁是否区分临时/永久”尚未确认。

当前 `user_account` 测试结构只有 `id/phone/password_hash/source/created_at`；`User` 实体无状态。管理端 `UserController` 为空类。小程序登录由 `UserAuthServiceImpl` 完成，HTTP 拦截器只检查 USER Token 本身，没有逐请求读取账号状态。管理员权限目录在 `AdminPermissionCodes`、`docs/sql/admin.sql` 以及管理端测试结构中。

## 拟定方案

1. 本版先采用**永久封禁，直到管理员手动解封**，不设置到期时间、不提供临时封禁。新增 `user_account.status VARCHAR(16) NOT NULL DEFAULT 'ACTIVE'`，仅 `ACTIVE/BANNED` 两值。交付幂等增量 SQL 供人工在运行库执行；更新相关测试结构，不在本次执行生产迁移。已有数据默认 `ACTIVE`。
2. 新增管理端 `GET /api/admin/users`、`GET /api/admin/users/{id}`、`PUT /api/admin/users/{id}/status`。分页沿用 `PageParam`（默认 1/10，size 最大 1000，`-1` 全量）；手机号模糊匹配、注册来源 `UserSourceEnum` 精确匹配，未知来源返回 400；按 `created_at DESC,id DESC` 排序。响应只含 `id/phone/source/status/createdAt`，不含密码散列。不存在的详情/状态更新返回 404。PUT 体 `status` 必填，值限 `ACTIVE/BANNED`；重复设置同一状态可成功且无额外会话操作。
3. 两个读取操作要求 `biz:user:read`，状态更新要求 `biz:user:status`，均沿用现有 ADMIN 会话拦截器；初始密码未改的管理员不能访问。将权限码加入内置目录，并在基础 SQL 与增量 SQL 中幂等插入权限定义。状态更新在业务层再次授权，保持管理员角色权限动态生效。
4. 封禁成功后注销该用户全部 USER Token；小程序登录/注册入口拒绝 `BANNED` 用户，包含并发创建冲突后读到被封禁账号的路径。小程序受保护请求逐次读取用户状态，拒绝封禁/不存在用户的 Token，以覆盖封禁与登录并发竞态；公开验证码与登录入口仍可访问。解封不恢复已注销 Token，需重新登录。
5. 不改其他已有管理端或小程序 API 的请求/响应字段；将新管理端三项操作准确加入 SpringDoc，声明 Bearer、权限码及筛选字段。不引入新依赖或第三方服务。
