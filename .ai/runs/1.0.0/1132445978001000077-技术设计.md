## 一、需求摘要

`POST /api/miniapp/pets/{id}/health-records` 新增记录。类型为 `VACCINE/DEWORM/WEIGHT/OTHER`，字段包括类型、标题、记录日期、备注、下次提醒日期。只有宠物归属人可添加；记录日期不得晚于当天。合法记录创建后可从响应取得并在后续列表接口查询；非归属宠物统一返回“不存在”；未来日期拒绝。

## 二、现有实现分析

小程序已具备宠物创建、分页列表、详情和编辑，`PetMapper` 可按 `id + owner_id` 查询，登录态由 `PetTownToken.USER` 提供。仓库未发现健康记录表、实体、Mapper、SQL 或接口。运行库 `pet` 的权威 DDL 仍缺失，用户此前表示由其后续执行宠物表 SQL。

## 三、建议技术方案

1. 新建 `pet_health_record` 表：`id BIGINT` 自增主键、`pet_id BIGINT NOT NULL`、`record_type VARCHAR(16) NOT NULL`、`title VARCHAR(100) NOT NULL`、`record_date DATE NOT NULL`、`notes VARCHAR(2000) NULL`、`next_reminder_date DATE NULL`、`created_time DATETIME NOT NULL`、`updated_time DATETIME NOT NULL`；索引 `(pet_id, record_date, id)`。请求字段仍为 `type`，列名采用 `record_type` 规避 SQL 关键字冲突。不在当前未知生产 `pet` DDL 上臆加外键或级联删除。
2. `module-business` 增加健康记录实体与 Mapper，复用 MyBatis Plus 自增 ID、时间填充；`module-miniapp` 增加请求 DTO、类型枚举、完整响应及创建服务/Controller。新 Mapper 位于已有 `com.pettown.business.pet.mapper` 扫描路径，无需改启动扫描。
3. 请求中 `type`、`title`、`recordDate` 必填；标题去首尾空格，1–100 字；备注可空且最多 2000 字；`nextReminderDate` 可空，不新增它与记录日期的先后关系；记录日期按应用当前日期校验不得在未来。`WEIGHT` 类型暂不新增数值字段，因为 TAPD 只列出上述五个字段。
4. 创建事务内以 `id + owner_id` 查询宠物并锁定行，再插入以该宠物 ID 关联的新记录；未查到统一 `NOT_FOUND`（HTTP 404，“宠物不存在”）。不接收客户端 ownerId。成功返回 HTTP 201、资源地址及含 ID 的完整记录。
5. 交付新表待执行 SQL 和 H2 测试结构；**不执行运行库建表或迁移**。用户对照真实运行库 `pet` 结构后自行建表。

## 四、影响模块与文件

`module-business` 健康记录实体/Mapper；`module-miniapp` Controller/DTO/服务/响应；`pettown-boot/miniapp` Mapper 扫描与接口测试；`docs/sql` 待执行建表 SQL；小程序测试 schema。App 与 admin 端现有路径不改变。

## 五、接口与数据模型变更

新增 POST 路由，不修改现有宠物接口。建议请求 JSON 为 `type`、`title`、`recordDate`、`notes`、`nextReminderDate`。响应为 `id`、`petId`、上述字段及创建/修改时间。后续 TAPD 1132445978001000078 列表接口依赖本表，但不在当前项提前开发。

## 六、权限与安全考虑

沿用已存在的小程序 Bearer 登录检查，SQL 以宠物 ID 与登录用户归属同时过滤；他人宠物与不存在宠物同一 404 响应，不暴露存在性。数据库插入时使用服务端查到的 petId，不接受客户端归属参数。

## 七、兼容性与数据迁移

新表独立，不修改旧表。建表 SQL 需在部署此接口前由用户执行；不自动迁移。没有真实 MySQL `pet` DDL，建表前需核对 `pet.id` 类型、字符集、引擎及现有命名。当前方案不添加外键，未来若有宠物删除业务，需单独明确健康记录保留/清理规则。

## 八、异常处理与可观测性

参数非法沿用现有 HTTP 400；宠物不存在或非本人统一 HTTP 404。日志不写入备注或敏感内容。可依现有请求追踪 ID 排查失败。

## 九、测试策略

先写接口红灯：本人合法创建、四种类型、响应与入库字段；实现后测试非本人/不存在统一 404 且无记录、匿名拒绝、未来日期/缺失字段拒绝、当天允许、可选字段、OpenAPI 声明。执行小程序测试、全仓 `./gradlew build`、SQL H2 MySQL 模式语法检查与逐文件审查。

## 十、回滚方案

回滚新增路由、服务、实体扫描；已写入健康记录保留，不自动删表或删数据。数据库结构回退需独立评审。

## 十一、备选方案

复用宠物表 JSON 字段会修改既有表且不利于类型、日期查询，不采用。直接通过客户端传 ownerId 会形成越权风险，不采用。

## 十二、假设与待确认问题

- 标题、类型、记录日期按必填处理；备注和下次提醒日期可空。标题 100 字、备注 2000 字为拟定技术上限，请审批时一并确认。
- 未来记录日期的“当天”按应用服务器配置的时区判断；若生产时区不是业务时区，部署配置需校正。
- TAPD 未要求体重数值字段、提醒日期先后约束、外键或宠物删除策略，本项不额外加入。
