## 需求与现状

TAPD 要求 `DELETE /api/miniapp/pets/{id}` 逻辑删除宠物，并将其健康记录一并标记删除；删除后列表和详情不再返回，数据库保留记录供审计。前置的健康记录新增、列表接口已在本地交付。现有 `pet` 和 `pet_health_record` 实体、测试结构与待人工执行的建表 SQL 均无软删列；现有宠物列表、详情、编辑、创建数量限制以及健康记录新增、列表均未排除已删行。

## 拟定实现

1. 为 `pet`、`pet_health_record` 各增加 `deleted INT NOT NULL DEFAULT 0`。编写仅供用户核对后执行的 MySQL 增量 SQL，同步更新本仓库新库建表 SQL 和相关 H2 测试结构；本次不连接运行库或执行迁移。两个实体使用既有 MyBatis-Plus `@TableLogic` 约定，使常规读取、更新和数量统计自动排除已删行。共享 `Pet` 查询的 App 端也随之不再暴露已删宠物，不新增 App 路由。
2. 新增小程序 `DELETE /api/miniapp/pets/{id}`，沿用 USER Bearer 会话拦截器。服务层在事务内按 `id + owner_id + deleted=0` 锁定宠物行，然后逻辑删除宠物及该宠物尚未删除的健康记录；失败则整笔回滚。只允许归属用户删除；他人宠物、不存在或已删宠物统一返回相同 404，重复删除也返回 404。成功返回既有统一结果格式 HTTP 200，不返回宠物内容。
3. 删除后宠物列表、详情、编辑、创建数量上限及健康记录新增、列表均按未删状态生效。删除释放该用户 20 只宠物的名额；已删记录仍留在数据库中。数据库唯一自增 ID 不复用，不提供恢复接口。
4. 先验证新 DELETE 路由缺失的红灯，再覆盖归属用户删除、两表标志与数据保留、列表详情不可见、健康记录接口不可访问、创建名额、他人/不存在/重复删除一致 404、匿名/ADMIN Token 401、事务回滚及并发写入边界。验证小程序和 App 相关回归、OpenAPI、全仓 `./gradlew build`、SQL/差异检查，并逐文件自审。
