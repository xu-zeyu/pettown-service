## TAPD 验收与仓库现状

TAPD 要求 `PUT /api/admin/system/accounts/{id}` 可改显示名、手机号、角色（分配角色需 `system:account:assign-role`），禁止修改自身角色（防提权）；验收：编辑生效，改角色后目标账号权限码同步变化；修改自己角色被拒绝。

仓库现状：`AdminAccountPageController`（/api/admin/system/accounts）已有分页/创建/启停/删除/重置密码，无编辑接口；业务层 `AdminService.updateAccount`（显示名/手机号，手机号变更使旧会话失效）与 `assignAccountRole`（单角色、null 解除、越权校验 `ensureSubset`、拒绝自身/超管目标）均已具备，且均在 `AdminAccessPolicy` 内先做 `authorizeWrite` 权限校验（分别为 `system:account:update` / `system:account:assign-role`）。

## 方案

1. 新增 `PUT /api/admin/system/accounts/{id}`，请求 `V1UpdateAccountRequest(displayName?, phone?, roleId?)`，字段为 null 即不修改；三者全空返回参数错误。响应返回编辑后的 `AccountResponse`。
2. 权限按操作分离，复用服务层策略校验（不再叠加单值注解，避免角色操作误要求 update 权限）：改显示名/手机号走 `updateAccount`（内部校验 `system:account:update`）；`roleId` 非空走 `assignAccountRole`（内部校验 `system:account:assign-role` 并做角色权限越权校验）。显示名/手机号任一提供时按当前值补全后整体提交（兼容服务层必填显示名的既有约束）。
3. 越权与自身保护沿用统一可管理边界 `requireManageableAccount`：**不能修改自身**、超级管理员或权限超出自身范围的账号；其中「禁止修改自身角色」为 TAPD 明确验收点，自改显示名/手机号同样按既有边界拒绝（待产品确认是否放开）。
4. 角色变更即时生效：目标账号有效权限逐请求实时解析（`AdminAccessPolicy.permissions`），换角色后其既有 token 的 `me.permissions` 立即变化；角色变更不踢会话（与既有 `assignAccountRole` 行为一致）；手机号变更使目标旧会话失效（`sessionVersion+1`，既有行为）。
5. 本接口不提供“清除角色”（roleId 为 null 视为不修改），如需解除关联可走既有兼容接口；记为待确认。
